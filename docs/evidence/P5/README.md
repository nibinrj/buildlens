# Build runner, dashboard and measurement evidence

Collected on 2026-10-19. The lab's flaky behavior and controlled duration are
**injected**. Read [results](../../results.md) for actual exported values and
their limits. This directory contains reviewed data; credentials, database dumps
and full private raw consoles remain outside tracked artifacts.

## Measurement boundary

The final fifty-build batch uses the freshly prepared job identified in
`driver-run.json` and the reviewed [lab source manifest](lab-source-manifest.json). This is an actual
Jenkins job loading a dated hashed local archive, not a normal Git-backed checkout.
The archive SHA-1 is an archive content identifier, not a Git tree object.
The separate [live PR proof](../P4/live-20261019/README.md) covers normal Git-backed
library/lab checkout and one real comment updated across two builds.

The first submission of an earlier measurement stopped before pipeline execution because the old job lost
its runtime script approval after a Jenkins restart. Its [checkpoint](failed-preflight.json)
and [console](failed-preflight-console.txt) are preserved and excluded from the
successful fifty-build batches. The existing reviewed Job DSL bootstrap was reapplied;
no Jenkins UI configuration was used. The driver did not silently retry a POST.

The initial successful fifty-build run is retained in `initial-batch/`. The final
batch follows startup and uses the final token-authenticated driver with its
integrated memory sampler and atomic checkpoint updates. The completed batch checkpoint, individual build CSV and database results are
exported with the exact queue IDs, executable numbers and BuildLens IDs. Memory
samples report the observed simultaneous sum and gaps, not an inferred absolute
peak. Unrelated kind clusters are excluded. The existing stack limits stay at
3392 MiB; CI runner/test Postgres limits are additional and run after measurement.

## Reproduction

```powershell
./tasks.ps1 up
./tasks.ps1 driver-token
./tasks.ps1 prepare-lab
# Use the exact job name printed by prepare-lab:
./tasks.ps1 drive 50 <prepared-job-name> SLOW_MILLIS=300
./tasks.ps1 dashboards
./tasks.ps1 dogfood-local
./tasks.ps1 demo-dump
./tasks.ps1 demo-restore <dump-path>
```

`prepare-lab` takes a new hashed snapshot from the sibling lab checkout and
applies its reviewed Job DSL without running builds. A container recreation
removes its temporary files, so prepare it again after `up`. The general driver's
default is `buildlens-lab/main`; the explicit prepared job is needed to reproduce
the recorded snapshot experiment. New source, history, caches and host load mean
new runs need not reproduce identical values.

## Remaining verification boundaries

Owner commit/push is needed before the normal `buildlens` multibranch job can
discover the new Jenkinsfile. The local adapter does not close that Git gate.
The isolated restore does not exercise owner-only live database replacement.
Natural flake precision/recall, production thresholds, sustained-load performance,
AWS deployment/spend and multiple-agent cost accounting remain unverified.
All four dashboards were also inspected in the signed-in browser. The saved
screenshots in `grafana/` are mid-batch views; their live totals can differ from
the final database export. The narrow side panel stacks charts vertically and
tables allow horizontal scrolling. API query/provisioning checks and visual
inspection are separate evidence.
